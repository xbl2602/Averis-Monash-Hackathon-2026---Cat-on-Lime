### #1 官方提交文件混入 2768 条内部测试数据
- **现象**：实测导出 `submission.json` = 3288 条，2768 条是 `pt1_…`~`pt14_…` 测试邮件。
- **根因**：`buildSubmissionDocument` 是"数据库里有什么就交什么"。以前库里只有官方 520 封，碰巧是对的；为了避免 Supabase 休眠，扰动测试数据也灌进了同一个库（决策 34），从那之后提交文件就悄悄变了。原本的完整性检查确实报了 `incomplete: true`，但 `missing=0 stale=0 invalid=0` 全是 0，很容易被当成误报忽略。
- **修法**：提交文件的成员资格改成锚定官方样例清单（`data/sample/inbox` 的文件名），不在清单里的一律不进。
- **验证**：实测导出 520 条、0 条测试数据、`incomplete: false`。

### #2 人工覆盖能悄悄改掉提交里的答案
- **现象**：就是上面"醒来先看"第 1 条的 email_004。
- **根因**：覆盖功能本身是对的（人比机器权威），但导出只报"还有几条没复核"，从不报"有几条被人改过"。
- **修法**：新增响应头 `X-Review-Overridden` / `X-Review-Overridden-Ids`、MCP 的 `review_overridden` 字段，以及导出前检查清单里新的一行"Every answer is the engine's own"（黄色软警告，不拦截下载，因为覆盖是合法的）。
- **验证**：实测导出头 `x-review-overridden: 1`、`x-review-overridden-ids: email_004`。

### #3 读不出/类型不对的附件被静默判 OK
- **现象**：扰动测试 pt1（把附件名里的 `_SI`/`_BL` 去掉）一直有 10 封不通过：冒充 BL 的发票、打不开的 BL，全被判成 **OK**。这是项目红线里的"装作成功"。
- **为什么重要**：官方 520 封附件名都带标记所以不受影响，但真实邮件（Gmail 同步、导入的文件）附件名不会按这个约定来。
- **根因**：按内容配对时，读不出的附件直接跳过、识别成"不是 SI/BL"的附件不占位，整封邮件看起来像"根本没有 BL"，落到"正文没明说要比对就判 OK"那条路。
- **修法**：配对函数如实返回"为什么缺"，调用方据此判 `wrong_doc_type` / `unreadable`。
- **验证**：pt1 **510/520 → 520/520**；官方 520 仍然 520/520。

### #4 运行状态切页面就丢失（你报的）
- **根因**：长耗时操作的"正在跑"和"跑完的结果"存在按钮所在组件自己的状态里。切页面 → 组件被卸载 → 状态没了，请求其实还在后台跑，跑完的结果也被丢掉。
- **修法**：新增 `app/_components/run-status.tsx`，挂在**根 Providers**。注意不能挂在 DashboardShell：`/dashboard` 和 `/features` 是两棵独立的路由树，各自渲染一份 shell，状态放 shell 里跨树切换照样丢。顶栏新增运行指示器（任何页面都能看到"还在跑 + 已经跑了多久"，点它回到那个页面）。同一个操作重复点会被拒绝，不会跑两遍。
- **覆盖范围**：Full pipeline 运行、Retry failed、devmode 清空/恢复。
- **局限**：整页刷新（F5）还是会丢——那需要服务端记录任务，属于大改，不在本轮范围。

### #5 SI/BL 对照表会被读串（你报的）
- **根因**：桌面宽度下，每个值没有自己的 SI/BL 标记，只有表格最上面一行表头。两个标红的行并排时，眼睛很容易把"上一行的 SI"和"下一行的 SI"配成一对，于是看到"EAST BRIGHT vs EAST BRIGHT，一样的怎么判不一致"。
- **修法**：每个值前面都带 `SI` / `BL` 小标签（所有屏宽），BL 列加一条竖分隔线。整块复制出来的纯文本也能分辨归属。

### #6 Word/Excel 附件里公司名和地址被粘成一行
- **现象**：`APRIL FINE PAPER TRADING` + 换行 + `ON BEHALF OF …` 变成 `TRADINGON BEHALF OF …`；`CLIFFORD PAPER INC` + `70 EAST STREET` 变成 `INC70 EAST STREET`。公司名连着地址被抽出来，和 BL 一比就是假的不一致。
- **根因**：
  - Word：`mammoth.extractRawText` 会直接丢掉段落内的软换行（Shift+Enter，XML 里是 `<w:br/>`）
  - Excel：解析时用 `\s+` 合并空白，把单元格内的换行（Alt+Enter）也压成了空格
- **为什么重要**：公司名和地址分行写，正是 Word/Excel 单证最常见的写法。
- **修法**：Word 改走 HTML 转换并保留换行；Excel 只合并横向空白、保留单元格内换行。
- **验证**：pt13 **5/12 → 10/12**，pt7 **6/12 → 8/12**；官方 520 封（含 8 个 docx、22 个 xlsx 附件）仍然 520/520。

### #7 Overview 数字点进去对不上
- **根因**：昨天把 Overview 头部改成只算官方 520 封，但列表页没跟着改，还混着 2768 封测试数据。
- **修法**：判定规则收敛到一个文件 `lib/shared/internal-data.ts`，统计 / 结果列表 / 冲突对 / 复核队列 / 提交导出全部默认只看官方样例。保留两个逃生口：接口传 `include_internal=true`，或者直接搜 `pt5_email_065` 这种 id。

### #8 引擎版本号没跟着规则改动 +1
- **根因**：项目约定"改规则就给 `PIPELINE_LOGIC_VERSION` +1"，用来让旧结果失效。昨天改了抽取和复核规则却没 +1，于是"Run and save"会认为旧结果仍然有效、跳过重算，修好的规则永远不会被套用到已有数据上；导出的"过期检测"也形同虚设。
